# 筆記、清單與資源回收生命週期

本文件把 `CONTEXT.md` 已定義的筆記、一般清單、關聯遊戲、庫外引用轉正、封存／還原及遊戲資源回收規則，落成可實作的狀態機、交易邊界與並行不變式。它不是 migration 或程式碼；實作時 `supabase/migrations/` 仍是唯一 schema 真本。

資料實體的共同外部身分與遊戲生命週期以「MVP 資料模型與不變式」為準；媒體原檔、縮圖與 Storage 孤兒清理由「媒體上傳、縮圖與生命週期」定義。本文件不改變既有產品行為，只補上實作前缺少的事件、失敗路徑及衝突語意。

## 裁決摘要

- 新筆記及新清單先是瀏覽器內草稿。空白新筆記永不建立資料列；新清單直到加入第一個成員才以單一交易建立清單與成員。
- 既有筆記清空後進入用戶端「待確認移除」，不把空字串寫入伺服器。只有應用程式內離開且確認移除，才軟移除原資料列；直接關閉、斷線或選擇保留都讓伺服器舊內容繼續成立。
- 一般清單、清單成員、關聯遊戲、筆記與遊戲都以原資料列表達生命週期，不為封存、軟移除或資源回收建立資料副本。還原只清除對應時間戳記。
- 一般清單名稱在一般與封存狀態共用唯一性。建立同名清單不會覆寫或另建；若命中封存清單，只回傳還原入口。
- 清單與關聯使用建立當下的穩定遊戲引用；來源支援的庫外遊戲以外部遊戲身分為目標，手動遊戲可直接以遊戲 ID 為目標。日後連結來源只建立兩者的解析關係，既有清單成員及關聯資料列不搬移。
- 關聯遊戲只保存一筆無方向關係，兩端使用相同的穩定遊戲引用並以固定順序存放。從任一端解除或還原都是同一資料列的狀態轉移。
- 所有會改寫既有狀態的命令都帶 `expectedVersion`；過期命令拒絕並保留用戶端尚未送出的內容。所有可重試命令另帶 `commandId`，同一命令重送只回放原結果，不重複產生副作用。
- 遊戲移入資源回收區只設定 `games.trashed_at`。筆記、媒體、標籤、清單成員、關聯與外部身分均不改寫；還原因此能原樣恢復整個聚合。

## 詞彙與資料邊界

| 詞彙 | 定義 |
|---|---|
| 草稿 | 只存在目前瀏覽器畫面的未持久化輸入；重新載入、直接關閉或斷線後自然消失。 |
| 穩定遊戲引用 | 清單或關聯建立當下的權威目標，可為外部遊戲身分或遊戲 ID；一旦保存就不因轉正或連結來源而改寫。 |
| 解析後遊戲 | 穩定遊戲引用在讀取當下所連到的遊戲條目；可能不存在、位於一般收藏庫或位於資源回收區。 |
| 軟移除 | 保留原資料列與內容，只設定 `removed_at`；一般讀取排除它。 |
| 封存 | 一般清單的軟移除名稱；保留名稱、成員及項目說明，只設定 `archived_at`。 |
| 資源回收 | 遊戲條目的生命週期狀態；只設定 `trashed_at`，不代表資料或 Storage 物件已刪除。 |
| 預期版本 | 命令送出前用戶端最後看見的單調遞增版本；資料庫只在目前版本相同時接受改寫。 |
| 命令識別碼 | 一次使用者意圖的 UUID。網路重試沿用同一值；新的點擊或新的意圖使用新值。 |

草稿屬於介面狀態，不建立伺服器草稿表。伺服器只保存已成立的筆記、清單、成員、關聯及遊戲；用戶端關閉造成的草稿消失不是刪除，也不需背景清理。

## 共用命令與並行規則

### 版本檢查

每筆可變實體都有單調遞增的 `version`。更新、軟移除、封存及還原命令在短交易內以資料列鎖或 compare-and-set 執行：

```text
命令(resourceId, expectedVersion, commandId)
                    │
                    ▼
             讀取命令紀錄
        ┌───────────┴───────────┐
        │同一命令已成功          │未見過
        ▼                       ▼
   回放原結果             鎖定目標資料列
                            │
                  ┌─────────┴─────────┐
                  │版本相同            │版本不同
                  ▼                   ▼
             寫入＋version+1      VersionConflict
                  │              不寫入任何資料
                  ▼
             保存命令結果
```

- `version` 在移除、封存、資源回收及還原時都繼續增加，不因回到先前的可見狀態而重設，避免 ABA 問題。
- `commandId` 與擁有者、命令種類及目標綁定。同一識別碼搭配不同 payload 時回 `LifecycleIdempotencyConflict`，不能把第一個結果套到第二個意圖。
- 成功命令寫入 `command_receipts`，至少保留到其目標資源永久刪除；MVP 沒有這些資源的永久刪除，因此 receipt 不自動清除。receipt 只保存輸入 digest 與領域結果，不保存筆記原文或項目說明。
- `LifecycleVersionConflict` 必須回傳目前版本與目前生命週期狀態，但不自動覆寫編輯器內容。介面暫停自動儲存，讓擁有者選擇載入伺服器版本，或在看過差異後以最新版本明確重送自己的內容；MVP 不做自動合併。
- 同一成功命令因回應遺失而重送時，回傳原本的資源 ID、版本及狀態。不得再增加版本、再寫一筆資料或再次顯示成新的操作。
- 不同命令先後要求相同終態，例如兩個分頁都要求封存同一清單，後到者若版本過期仍回衝突；不能以「反正已封存」掩蓋它可能基於過期畫面執行的事實。

### 交易與外部副作用

- PostgreSQL 交易內只做資料庫讀寫與約束檢查，不等待瀏覽器、BGG、IGDB 或 Storage。
- 每個命令的權威成功邊界是資料庫交易提交；提交前不能在介面顯示成功。
- 庫外封面縮圖若需取得或重建，使用媒體 module 的冪等工作與私有 Storage adapter。縮圖失敗不得回滾已成立的清單成員；成員以明確的無縮圖狀態顯示。
- 資料庫唯一約束是名稱、成員及關聯去重的最終仲裁者。應用程式將約束衝突轉成命名領域結果，不把原始 PostgreSQL 錯誤洩漏給介面。

## 筆記

### 權威資料

`notes` 至少保存 `game_id`、Markdown `content`、`version`、`removed_at`、建立與修改時間。任何未軟移除資料列的 `trim(content)` 必須非空；軟移除仍保留清空前的原文，不以空字串取代。

新筆記建立使用草稿產生的 `commandId` 作為冪等鍵。同一遊戲內重送同一建立命令最多產生一則筆記；不同命令即使內容相同仍是不同筆記，因為產品允許多則獨立筆記。

### 用戶端狀態機

```text
                         輸入非空白
       new_empty ─────────────────────────► dirty_nonblank
          │                                      │
          │ 離開／關閉：不寫入                    │ debounce
          ▼                                      ▼
       discarded                              saving
                                             │    │
                                  成功       │    │ 失敗／衝突
                                             ▼    ▼
                                           saved failed
                                             │      │
                                    編輯非空 │      │ 重試
                                             ▼      └────► saving
                                      dirty_nonblank
                                             │
                                       清空／全空白
                                             ▼
                                      removal_pending
                                         │       │
                              再輸入非空白│       │應用程式內離開
                                         │       ▼
                                         │   詢問移除／保留
                                         │      │       │
                                         └──────┘       ├─保留──► saved（回填伺服器舊文）
                                                        └─移除──► removing ─► removed
```

- `new_empty` 與尚未成功建立的 `dirty_nonblank` 都沒有 note ID。若第一次儲存失敗，文字留在編輯器並顯示 `failed`；離開時依未儲存內容規則提示。
- `saved` 的編輯器保存最後確認的伺服器內容與版本。每次停止輸入後才送出最新非空白內容；舊的 debounce 計時器必須取消。
- 既有筆記變成空白時立即停止自動儲存並進入 `removal_pending`。此狀態保留最後確認的非空白內容與版本，供「保留」回填及「移除」命令使用。
- 直接關閉分頁、瀏覽器崩潰或斷線不會觸發移除命令；重新開啟時從伺服器讀回清空前內容。
- 儲存中要求離開時，先等待目前請求在有限時間內完成。成功才離開；失敗、逾時或版本衝突時顯示仍有未儲存內容，且不建立離線佇列。
- 多個儲存請求不得同時代表同一編輯器的權威結果。若網路造成回應反序，用戶端只接受目前 attempt 的結果；伺服器版本檢查則阻止較舊內容覆寫較新內容。

### 伺服器狀態機與交易

```text
不存在 ── create(nonblank) ──► active
                                  │  ▲
                           remove │  │ restore
                                  ▼  │
                                removed

active ── update(nonblank, expectedVersion) ──► active(version+1)
active ── update(blank) ──► NoteContentBlank（不寫入）
```

- `createNote` 驗證遊戲仍存在且未移入資源回收區，再以一個交易建立非空筆記與命令結果。
- `updateNote`、`removeNote`、`restoreNote` 都鎖定同一 note 資料列並核對 `expectedVersion`。移除只設定 `removed_at`；還原只清除它，原文與建立時間不變。
- 已軟移除筆記不接受一般內容更新。要修改必須先還原，避免一個請求同時隱含兩種使用者意圖。
- 筆記的立即復原入口可隨介面通知消失，但資料不永久清除。MVP 沒有獨立筆記資源回收頁；因此通知消失後不承諾另一個還原入口。

## 一般清單與成員

### 權威資料與穩定引用

`lists` 保存顯示名稱、正規化名稱、`version` 與 `archived_at`。正規化名稱在所有一般與封存清單中永久唯一；封存不釋放名稱。

`list_memberships` 保存 `list_id`、穩定遊戲引用、選填短說明、`version` 與 `removed_at`。目標恰為下列之一：

- 已連結來源或庫外的遊戲：`external_game_identity_id`。
- 未連結來源的手動遊戲：`game_id`。

同一清單與同一穩定引用只保留一筆成員資料列，包含軟移除資料列。再次加入已軟移除成員時回傳「可還原」結果；只有明確還原才清除 `removed_at`，不建立第二列。

新加入已連結來源的正式遊戲時，命令使用其外部遊戲身分；未連結來源的手動遊戲使用遊戲 ID。手動遊戲日後連結來源不改寫既有 `game_id` membership，因此新增、查重及讀取必須把「該 game ID」與「它目前連結的 external identity ID」視為同一解析目標。同一清單不可同時有兩筆解析到同一遊戲的 active membership。

### 新清單草稿與第一次持久化

```text
開啟建立畫面
      │
      ▼
client_draft（名稱可空、成員為空；資料庫無列）
      │                         │
      │離開                     │選擇第一個成員
      ▼                         ▼
提示放棄；關閉／斷線自然消失   createListWithFirstMember
                                │
                    正規化名稱＋解析穩定引用
                                │
                  ┌─────────────┼─────────────┐
                  │名稱未使用    │一般清單同名  │封存清單同名
                  ▼             ▼             ▼
          同交易建立清單＋成員  ListNameInUse  ArchivedListFound
                                              │
                                      顯示名稱、成員數、還原
```

- 只有名稱、沒有成員時不呼叫建立命令。提示能否顯示不影響資料結果；直接關閉或斷線後不留下空清單。
- `createListWithFirstMember` 在單一交易內插入清單、第一個成員及命令結果。任一約束失敗全部回滾，不得留下空清單。
- 命中封存清單時，第一次建立命令不自動還原，也不把草稿中選取的成員加入舊清單；介面先顯示封存清單的名稱、成員數與還原按鈕。擁有者確認還原後才執行獨立的 `restoreList`，避免把「還原既有內容」與「新增成員」合成未被確認的副作用。
- 已成立的一般清單日後移除最後一個成員仍可保持空清單。未持久化規則只適用於首次建立；既有清單不因最後成員被移除而自動封存或刪除。

### 成員與清單生命週期

```text
                     add first member
client_draft ─────────────────────────► active list
                                           │  ▲
                                   archive │  │ restore
                                           ▼  │
                                      archived list

不存在 membership ── add ──► active membership
                                  │  ▲
                           remove │  │ restore
                                  ▼  │
                            removed membership
```

- `addListMember` 交易先鎖定一般清單並核對清單版本，再鎖定目標 game／external identity，檢查同一穩定引用及所有目前等價引用後才建立成員；成功時同時增加清單版本。封存清單拒絕成員異動。
- `updateListMemberDescription`、`removeListMember` 與 `restoreListMember` 鎖定成員並核對成員版本；增刪成員另增加清單版本，讓基於過期成員集合的封存或後續寫入可見衝突。
- `archiveList` 鎖定清單並核對版本，只設定 `archived_at`。所有一般及已軟移除的成員、短說明與庫外封面引用都不變。
- `restoreList` 鎖定同一資料列並清除 `archived_at`。名稱唯一性從未釋放，因此不需改名、合併或搬移成員。
- 封存清單有任何解析後的庫內遊戲時，讀取端從成員遊戲頁列出還原入口。沒有任何庫內遊戲時，只有建立畫面的正規化名稱查詢會揭露它；兩條入口都呼叫同一 `restoreList`。
- 遊戲移入資源回收區不改成員。讀取端把解析後位於資源回收區的成員顯示為灰階並提供遊戲還原；它仍算庫內成員，因此也能成為封存清單的還原入口。

## 關聯遊戲

關聯遊戲不是每個遊戲各自持有的兩筆清單成員，而是一筆 `game_relations`。兩端都是穩定遊戲引用；寫入前先轉成帶種類的 canonical key，按 key 排序後保存為 `left_ref` 與 `right_ref`。

資料庫保證：兩端不同、`left_ref < right_ref`，且無論 active 或軟移除，同一無方向配對只有一列。關聯可保存一段共用短說明；因為關係沒有方向，不能從兩端寫入互相矛盾的兩份說明。

```text
X 頁新增 Y                         Y 頁新增 X
      │                                  │
      └──── normalize refs＋sort pair ───┘
                         │
                         ▼
              同一筆 undirected relation
                         │
                  ┌──────┴──────┐
                  │ active       │ removed
                  ▼              ▼
             兩側都顯示      兩側都隱藏

active relation ── remove from either side ──► removed relation
       ▲                                               │
       └──────── restore from undo ────────────────────┘
```

- `addRelation`、`removeRelation`、`restoreRelation` 與說明更新都核對 relation 版本。兩端都解析為庫內遊戲時，增刪另增加兩個遊戲的聚合版本；一端仍是庫外引用時只增加目前庫內端的版本。
- 新增時先鎖定兩端所屬的 game／external identity，並把每端目前等價的 game ID 與 external identity ID 納入查重；若同一解析後配對已 active，回傳既有關係；若已軟移除，回傳可還原結果，不建立第二列。
- 任一端解析為資源回收遊戲時，關係資料仍 active；一般端顯示灰階的資源回收對象與還原入口。還原遊戲後自動恢復正常顯示。
- 具方向性的敘述不得塞進 relation 短說明來模擬方向；應改用一般命名清單。
- 手動遊戲第一次連結來源時，若它目前的 `game_id` 引用與該外部身分引用會讓同一清單出現重複成員，或讓關聯折疊成自我／重複關係，連結交易回 `SourceLinkReferenceConflict` 並保持所有資料不變。介面列出需先解除的 membership／relation；不得靜默刪除、合併兩段說明或建立自我關係。

## 庫外引用轉正

外部遊戲身分是來源支援遊戲的永久引用錨點。一般清單成員及關聯遊戲從一開始就指向它；「庫外」只是該身分目前尚未解析到遊戲條目的讀取狀態，不是另一份將來要搬移的成員資料。

```text
external_game_identity
          │
          ├── list membership A
          ├── list membership B
          ├── undirected relation C
          └── local WebP cover thumbnail
          │
          │ create／link game（單一 DB 交易）
          ▼
external_game_identity ─────────► game
          │                         │
          ├── 原 membership A ─────┤ 讀取時解析為正式遊戲
          ├── 原 membership B ─────┤
          └── 原 relation C ───────┘
```

- 轉正交易只建立或鎖定遊戲、鎖定外部身分、驗媒介與唯一性，再檢查 game ID／external identity ID 解析後不會形成重複 membership 或自我／重複 relation，最後設定一對一連結；清單成員與關聯資料列零更新。
- 並行轉正由 `external_game_identities(provider, source_id)` 與遊戲連結唯一約束仲裁。勝出的請求建立連結；其餘請求讀回同一一般遊戲，或在它已位於資源回收區時回傳還原提示。
- 庫外 WebP 縮圖仍附屬外部身分，可在正式來源封面可用前作為降級顯示。轉正不刪 Storage 物件；正式來源封面原檔及其縮圖由媒體 module 管理。
- 遊戲日後移入資源回收區時，外部身分仍解析到同一遊戲，所有清單位置顯示資源回收狀態，不退回成另一筆庫外引用。
- 手動遊戲連結已有庫外引用的外部身分時也走相同交易。若該身分已連到另一個一般或資源回收遊戲，或連結會形成解析後引用衝突，整體拒絕，原手動遊戲及所有關係不變。使用者先從衝突清單選擇保留的 membership／relation 並解除另一筆後，才以最新 game 版本重試連結。

## 遊戲資源回收

遊戲只有 `active` 與 `trashed` 兩個 MVP 狀態。沒有 `deleting`、永久刪除或自動清空狀態；Storage 也沒有對應刪除步驟。

```text
active game
    │
    │ 顯示目前筆記、照片、附件、清單、關聯數量
    │ confirm moveToTrash(expectedVersion)
    ▼
trashed game
    │  games.trashed_at 以外全部不變
    │  外部身分唯一性仍被占用
    │  清單／關聯顯示灰階＋還原入口
    │
    │ restore(expectedVersion)
    ▼
active game（原資料、關係與 Storage 指標重新可見）
```

- 確認畫面的數量是讀取時快照，用來說明影響，不是刪除清單。確認後即使另一分頁剛新增內容，移入資源回收區仍只隱藏當下完整聚合，不會漏刪或部分刪除，因為根本沒有級聯刪除。
- `moveGameToTrash` 在一個短交易內鎖定 game、核對版本並設定 `trashed_at`。不得更新筆記、媒體、標籤、平台、清單、關聯、外部身分或任何 Storage 指標。
- `restoreGame` 鎖定同一 game、核對版本並清除 `trashed_at`。因外部身分與所有子資料從未釋放或搬移，還原不需重建、合併或從備份複製。
- 一般遊戲頁的內容編輯命令在遊戲位於資源回收區時回 `GameTrashed`；清單成員及關聯仍可從其他一般遊戲或清單的脈絡移除／還原，因它們有自己的生命週期。
- 建立或連結命中資源回收遊戲時回傳該遊戲 ID 與還原提示，不建立第二筆。資源回收狀態不釋放任何來源唯一鍵或名稱比對候選。

## 交易矩陣

| 命令 | 同一交易內必須一起成立 | 交易外工作 | 失敗時保留 |
|---|---|---|---|
| `createNote` | 非空 note＋命令結果 | 無 | 用戶端草稿文字 |
| `updateNote` | 版本核對＋非空內容＋版本增加 | 無 | 伺服器舊文與編輯器新文 |
| `removeNote`／`restoreNote` | note 狀態＋版本＋命令結果 | 無 | 原內容與原狀態 |
| `createListWithFirstMember` | list＋第一個 membership＋命令結果 | 庫外縮圖另行處理 | 整個用戶端草稿 |
| `add`／`remove`／`restoreListMember` | membership 狀態＋membership/list 版本 | 庫外縮圖另行處理 | 原清單與成員狀態 |
| `archiveList`／`restoreList` | list 狀態＋版本＋命令結果 | 無 | 名稱、所有成員與說明 |
| `add`／`remove`／`restoreRelation` | 唯一無方向 relation＋版本；可解析端的聚合版本 | 庫外縮圖另行處理 | 原關聯及說明 |
| 外部引用轉正 | 外部身分唯一性＋game 建立／連結 | 來源取得與封面 ingest | 所有既有 membership/relation |
| `moveGameToTrash`／`restoreGame` | game 狀態＋版本＋命令結果 | 無 Storage 工作 | 全部子資料、關係及物件指標 |

任何列若在提交前失敗都完整回滾。外部縮圖工作可以獨立失敗並重試，但不能把已提交的成員冒充成未建立；介面須把「成員已加入、縮圖目前不可用」顯示成可區分的結果。

## 命名結果與失敗語意

| 結果／錯誤 | 使用者語意 | 資料語意 |
|---|---|---|
| `LifecycleVersionConflict` | 畫面資料已變更，保留目前輸入並要求重新載入或明確重送 | 零寫入 |
| `LifecycleIdempotencyConflict` | 同一重試識別碼被用於不同操作 | 零寫入，記錄技術事件 |
| `NoteContentBlank` | 空白內容不能建立或更新；既有筆記改走移除確認 | 零寫入 |
| `UnsavedNote` | 離開前仍有未完成內容 | 伺服器舊內容不變 |
| `ListNameInUse` | 同名一般清單已存在 | 不建立清單或成員 |
| `ArchivedListFound` | 同名封存清單可還原 | 回傳清單 ID、名稱、成員數與入口，不自動還原 |
| `ListMemberExists` | 成員已在清單中 | 回傳既有成員，不建立第二列 |
| `RemovedListMemberFound` | 成員曾被移除，可明確還原 | 原資料列維持移除 |
| `RelationExists` | 兩款遊戲已相關 | 回傳既有無方向關係 |
| `RemovedRelationFound` | 關係曾解除，可明確還原 | 原資料列維持移除 |
| `SourceLinkReferenceConflict` | 來源連結會讓清單成員重複，或讓關聯變成自我／重複關係 | 連結、成員與關係全部不變；回傳衝突資源 ID |
| `GameTrashed` | 先還原遊戲才能編輯內容 | 零寫入，回傳還原入口 |

所有失敗都帶 request ID 供伺服器記錄。log 可記錄命令種類、非敏感資源 ID、版本、結果與 duration；不得記錄筆記原文、清單項目說明、signed URL 或第三方回應內容。

## 可驗證不變式

### 資料庫約束與交易測試

- active 筆記的 `trim(content)` 永不為空；清空既有筆記不會在確認前改寫伺服器內容。
- 同一筆記的兩個並行更新使用相同 `expectedVersion` 時，恰有一個成功；失敗者內容不會覆寫成功者。
- 同一 `commandId` 重送不產生第二則筆記、第二張清單、第二個成員或第二條關聯。
- 一般與封存清單不能有正規化後同名的兩筆資料；封存不釋放名稱。
- `createListWithFirstMember` 不可能留下沒有第一個成員的新清單；既有清單移除最後成員後則允許保持空白。
- 一個清單對同一穩定遊戲引用最多一筆 membership，包含已軟移除資料列；同一清單也不能有兩筆 active membership 解析到同一正式遊戲。
- 一組無方向穩定引用最多一筆 relation；`X—Y` 與 `Y—X` 命中同一列，且不能建立 `X—X`。連結來源前的交易檢查保證引用等價類改變後仍不產生解析後重複或自我關係。
- 庫外引用轉正時，既有 membership 與 relation 的主鍵、說明、移除狀態及版本均不改變。
- 移入資源回收區及還原只改 game 的生命週期欄位與版本；所有子資料列數、外部身分、關係及 Storage object path 前後完全相同。

### 關鍵整合情境

1. 建立空白新筆記後離開，不出現資料列；輸入非空內容後第一次回應遺失，重試仍只有一則筆記。
2. 清空既有筆記、斷線並關閉分頁，重新開啟仍看到清空前內容；清空後選擇移除則保留原文的軟移除列，立即復原可原樣顯示。
3. 筆記在兩分頁同時編輯，第一個成功寫入後，第二個收到 `LifecycleVersionConflict`；第二個編輯器文字仍在且不自動覆寫。
4. 新清單只有名稱時關閉分頁，資料庫沒有空清單；加入第一個成員時 list 與 membership 同成同敗。
5. 建立名稱命中只有庫外引用的封存清單時，顯示舊名稱、成員數與還原入口；確認後還原同一 list ID，原說明與成員全在。
6. 從 X 新增 Y、同時從 Y 新增 X，最後只有一筆 active relation；從任一端解除後兩端都隱藏，立即復原後兩端都恢復。
7. BGG 庫外引用同時位於兩張一般清單及一條關聯；正式建立相同來源遊戲後三筆關係零更新，三處都解析到同一遊戲。
8. 遊戲移入資源回收區後，所有清單與關聯顯示灰階及還原入口；還原後筆記、圖片、附件、標籤、說明與關係主鍵完全不變。
9. 封存、還原、移除成員及移入資源回收區的成功回應各自遺失後，以同一 `commandId` 重送只回放原結果，版本不再增加。
10. 手動遊戲與待連結外部身分在同一清單各有一筆 membership，或兩者連結後會產生自我／重複 relation；來源連結零寫入並回傳全部衝突，解除其中一筆後重試才成功。

## 後續實作切面

- migration 以 PostgreSQL check／unique constraints、外鍵與受限 transaction function 守住跨表不變式；RLS 不是業務約束的替代品。
- module interface 只暴露本文件命名的使用者意圖與領域結果。Next.js Server Action 不直接組合多表寫入，也不把 Drizzle／PostgreSQL 錯誤傳到 Client Component。
- integration tests 優先覆蓋上述十個交錯情境；pgTAP 驗唯一性、check constraint、禁止級聯刪除及轉正零搬移。
- 行動版原型只決定提示、按鈕位置與衝突呈現，不得改變本文件的資料成功邊界。若原型證據要求不同產品行為，先回到新的決策票，不在實作中靜默偏離。
